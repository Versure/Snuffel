## Open vragen voor Jop

Geen vraag blokkeert het bouwen. Tussen haakjes staat wat we doen als Jop niets anders zegt.

1. **Schrijfrechten op de NAS-map.** De container draait als niet-root gebruiker met vaste uid/gid `1000:1000`. Op een Synology hoort `/volume1/docker/snuffel/pb_data` meestal bij jouw DSM-gebruiker (uid 1026 of hoger). Zonder aanpassing kan PocketBase daar niet schrijven en start de container niet. (Standaard: de README laat je de map één keer aan uid 1000 geven. Dat kan via SSH met `sudo chown -R 1000:1000 …` of via DSM → Configuratiescherm → Taakplanner als eenmalige taak met hetzelfde commando. Alternatief: in `compose.nas.yml` `user: "<jouw uid>:<gid>"` zetten. Dat is ook later nog om te zetten.)
2. **Release bij elke merge of alleen bij een versietag?** Het implementatieplan (hoofdstuk 6, vraag 1) kiest voor elke merge naar `main`. Dat nemen we over, met daarbij een handmatige knop (`workflow_dispatch`).

## Doel

Na M4 kan Jop de echte productie-image lokaal draaien met `docker compose -f deploy/compose.dev.yml up` en Snuffel openen op http://localhost:8090. Dat is dezelfde app als bij `npm start`, maar nu geserveerd door PocketBase. Elke pagina krijgt daarbij een Content-Security-Policy, zodat de browser zelf weigert om iets van buiten te laden. Na een merge naar `main` bouwt GitHub Actions de image en zet die op `ghcr.io/versure/snuffel`. De README beschrijft stap voor stap hoe Jop het project in Container Manager op de NAS zet, de eerste superuser aanmaakt, back-ups regelt, bijwerkt en terugzet. Daarna is Snuffel op de telefoon bereikbaar op `http://<nas>:8090`, via de thuiswifi.

## Risico's en open vragen

- **Inline kritieke CSS en de CSP.** De Angular-productiebuild kan in `index.html` een `<link … media="print" onload="this.media='all'">` zetten. `default-src 'self'` blokkeert die inline handler, waardoor de app zonder globale stijl laadt. Stap 3 controleert dit en zet `inlineCritical` zo nodig uit. De e2e (geen overtredingen, `body`-kleur, fonts) vangt een terugval op.
- **De fixture en de controletest.** Stap 3 voegt een extern plaatje in om te bewijzen dat de CSP blokkeert. Chromium meldt zo'n geblokkeerd verzoek mogelijk niet als `request`. Doet hij dat wel, dan keurt de auto-fixture de test af. Gebruik in dat geval alleen een inline `<script>`: dat geeft een `securitypolicyviolation` zonder netwerkverzoek. Versoepel de fixture **niet**.
- **Dubbele build in `verify`.** `check` bouwt al, en de PocketBase-webserver in de e2e bouwt opnieuw. Zo test `npm run e2e` los ook altijd de actuele code. Dat kost een halve tot een hele minuut extra. Wordt het te traag, dan kan een vlag (bijv. `SNUFFEL_SKIP_BUILD=1` vanuit `verify`) later helpen. Dat zou een afwijking zijn.
- **Eerste `npm run e2e` vraagt internet** (download van PocketBase van GitHub, ±15 MB). Daarna staat het binary in `pocketbase/bin/` en werkt alles offline. Achter de proxy in deze omgeving moet `fetch` het systeemcertificaat gebruiken (`NODE_EXTRA_CA_CERTS`). Lukt de download niet, dan stopt het script met een duidelijke melding, en niet met een stille skip.
- **Schrijfrechten op de NAS** (open vraag 1). Het meest waarschijnlijke struikelblok bij de eerste uitrol. De README krijgt daarom een eigen probleemoplossing.
- **`/_/` is bereikbaar op het hele thuisnetwerk.** Iedereen op de wifi ziet het inlogscherm van het beheer. Kies een sterk wachtwoord voor de superuser. Afschermen kan later via de DSM-firewall of een reverse proxy. Dat zetten we in de README.
- **Automigrate.** PocketBase kan bij wijzigingen via `/_/` zelf migratiebestanden in `--migrationsDir` schrijven. Op de NAS gebeurt dat binnen de container en gaat het bij een update verloren. Regel in M5 (README en CLAUDE.md): collecties alleen via migraties in de repo, nooit via `/_/` op de NAS.
- **PocketBase is nog geen 1.0.** De hook gebruikt de API vanaf 0.23 (`routerUse`, `e.request.url.path`, `e.response.header().set`). Bij een update van PocketBase moeten de server-e2e's eerst groen zijn.
- **Image-grootte en `npm ci` in Docker.** `npm ci` installeert ook de devDependencies (nodig voor de build), maar alleen in de build-stap. De runtime-image bevat alleen alpine, het binary en statische bestanden. Playwright downloadt bij `npm ci` geen browsers.
- **Later nodig, niet in M4:**
  - `npm start` met PocketBase-binary, dev-seed en proxy `/api` (M5). Dat gebruikt `tools/fetch-pocketbase.mjs` en `tools/serve-pocketbase.mjs` uit deze mijlpaal;
  - integratietests in `pocketbase/tests/` (M5) kunnen dezelfde serve-tool gebruiken;
  - `npm run content:build` in de build-stap van de Dockerfile (M6);
  - als `content/` later een volume wordt (implementatieplan 2.1): een extra mount in `compose.nas.yml`, de app blijft gelijk;
  - https via Tailscale of de reverse proxy van DSM (implementatieplan 6).

## Afwijkingen

1. **Branchnaam.** Er wordt gewerkt op `ccr-132bd3e0-fjewgu` in plaats van `feat/m04-container`, omdat de omgeving die branch oplegt. Noem dit in de PR.
2. **Tools in `.mjs` in plaats van TypeScript via `tsx`** (implementatieplan 1.1), om gelijk te blijven met de tools uit M1 en geen extra dependency toe te voegen.
3. **`test:tools` met een glob.** `node --test tools/` faalt in Node 24 (een map is geen testbestand). Het script is `node --test "tools/**/*.test.mjs"`; Node zelf werkt de glob uit, dus het werkt op elk platform.
4. **Kritieke CSS: inline `<script>`, geen `onload`.** De productiebuild zette geen `onload=`, maar een inline `<script>` (Beasties) dat `media="print"` omzet. Dat blokkeert de CSP net zo goed, dus `inlineCritical` staat uit in de `production`-configuratie (`scripts`, `minify` en `fonts` blijven aan).
5. **`/_/` heeft wel een CSP, maar niet die van ons.** PocketBase stuurt voor het beheerscherm zelf een CSP mee. De test controleert daarom dat `/_/` niet de app-CSP en geen `Referrer-Policy` van de hook krijgt; `/api/health` heeft helemaal geen CSP.
6. **Controletest alleen met een inline script.** Een ingevoegd extern plaatje wordt door de CSP geblokkeerd, maar Chromium meldt het wel als `request`, zodat de privacy-fixture de test afkeurt (zoals voorzien onder "Risico's"). Die test is weggelaten; de fixture is niet versoepeld.
7. **`serve-pocketbase.mjs` wist alleen een opgegeven `--data`.** Zonder `--data` gebruikt het `pocketbase/pb_data/local` en blijft die data staan (handig voor `serve:prod`). Verder start het met `--hooksWatch=false`.
8. **Dockerfile:** (a) de runtime-stap heeft geen vaste `--platform=linux/amd64` in `FROM` (BuildKit waarschuwt daarvoor); het platform komt uit `platform: linux/amd64` in de compose en `platforms: linux/amd64` in de workflow. (b) Een optioneel build-secret `extra_ca` (eigen CA voor een netwerk met een TLS-proxy) en `NODE_USE_ENV_PROXY=1` bij het ophalen van PocketBase. Zonder secret en zonder proxy verandert er niets; de release-workflow gebruikt ze niet. (c) Basisimages `node:24.22.0-alpine` en `alpine:3.24`.
9. **`compose.dev.yml` heeft `name: snuffel-dev`**, zodat project, container en volume een vaste naam hebben, los van de mapnaam `deploy`.
10. **`SNUFFEL_COMPOSE_OVERRIDE`.** De `globalSetup` en de containertests geven, als deze variabele gezet is, één extra compose-bestand mee met `-f`. Zo kan een netwerk dat proxy-instellingen voor de build nodig heeft die buiten de repo houden. Normaal is hij niet gezet.
11. **Versies van de actions:** `actions/checkout@v7`, `docker/setup-buildx-action@v4`, `docker/login-action@v4`, `docker/metadata-action@v6` en `docker/build-push-action@v7` (de nieuwste majors bij het bouwen).
